# 按目标找 build（2026-10-30 / 31）

构筑辅助「按目标找 build」（只在本机自用版）：给一个目标（魔上限、助手数、每秒回魔、总产出），选「最快达到某个值」或「某个时刻数值最高」，可选「要求能用某个法术」，程序从存档退位重开，按游戏公式推出最优的立场 / 阵营 / 显赫阵营 / 血统 / 佣兵模板 / 研究模板，并整局跑验证。研究和佣兵模板可以复制或直接存进游戏的模板库。

代码：`脚本/rg_optimize.py`（求解器，命令行也能跑）、`脚本/rg_depgraph.py`（依赖图）、`脚本/rg_sources.py`（列出某个目标的全部来源）、`脚本/rg_goal.py`（单次整局试跑 `Runner.run`、佣兵放格子、并行进程池）。引擎操作 `goal_start / goal_status / goal_stop`（`应用/build_engine.py`），子进程 `rg_app.py --opt-worker`。

## 为什么不是「每个组合整局跑一遍」

前两版的教训（都已弃用）：
- 暴力试组合（`rg_goal.Search`）：每个组合整局跑，慢；粗筛时所有阵营共用仙灵局的研究，不公平。
- 在一个状态上切标记估算：用的是别的阵营跑出来的状态，一局里攒出来的量（建筑数、产生的魔力、阵营币、点击）丢了；贪心一次只加一项，漏掉连锁；不管买不买得起（估 435 万，实跑 125 万）。

## 做法

### 1. 依赖图（`rg_depgraph.py` → `资料/依赖图（客户端4.3.14）.json`，打包时复制成 `build/calculation/depgraph.json`）
游戏的目标函数写得很规整：每个来源都是「if(拥有 X) 底数 += X.方法()」或「*= 1 + 0.01 × X.方法()」。脚本解析出每个来源，再读 X.方法() 的方法体（往下追两层），把它读的输入分三类：
- **中间量**：本身是当场算的公式（助手数、回魔、魔上限、产出、助手效率），递归连到那个目标的来源——例如「研究 B 按助手数加回魔」，提升助手数的项就经助手数连到回魔；
- **驱动**：一局里攒的量（建筑数 → 产出、产生的魔力 → 回魔、找到的阵营币 → 阵营币几率、施法、点击）；
- 其他：研究点数、考古、世系等级、时间、奖杯数，和这一局的 build 无关。

魔上限 83 个来源、助手数 100、回魔 101、产出 162，绝大多数都对上了存档编号。和目标（直接或经中间量）相连的研究、佣兵升级才进「精确比较」，其余只用来填空格。魔上限现在能选的相关研究只有 7 项、相关佣兵升级 6 个左右，所以下面可以穷举。

### 2. 在一个状态上求精确最优（`solve_static`）
在某个真实游戏状态上直接设定 build（立场 / 阵营 / 显赫阵营变量，各升级、血统、研究的拥有标记），用游戏公式重算目标——几毫秒一次，不推进时间。
1. 相关项先全部放上，去掉不起作用的；
2. **受限的组**（研究每个分支的格数——由游戏 `getResearchCap` 给出；佣兵编号 1–3 / 4–6 / 7–9 各 4 格、龙族只在每组第 4 格；佣兵的阵营币预算）**组内穷举全部合法子集**，其他组固定，取最好；各组轮流到不再变化；两个都受限的组再联合穷举；
3. 剩下的空格按「驱动」价值填：目标依赖哪个驱动、依赖多少（在这个状态上逐项关掉依赖该驱动的来源实测），每个候选对驱动速率提升多少（切标记重算产出 / 回魔 / 阵营币几率）；
4. 佣兵按贡献从大到小排进模板（龙族按游戏规则排最前），重要的占便宜的格位、先买。

佣兵价格用游戏自己的 `MercenaryUpgrade.getMercenaryFactionPrice`：普通阵营 = 组号³ × 格位^2.5 × 1000 个该阵营的币；泰坦 / 德鲁伊 / 无面者花另外两个阵营的币；龙族花矮人和卓尔的币 1e4 × 100^格位（DG7 要 1e12）。预算 = 这个状态里剩的 + 这一局已经花在佣兵上的。

### 3. 每个结构用自己的状态（闭环，`closed_loop`）
整局跑（`Runner.run`：退位 → 买立场、阵营、血统 → 显赫阵营 → 研究 → 佣兵按格子规则买，每 2 秒「全部购买」）→ 在**它自己跑出来的状态**上重求 → 再跑，直到方案不变（最多 4 轮）。到时间上限还买不起的佣兵升级 / 买不上的研究从候选里排除——但第一轮（估算给的方案只有和目标直接相关的研究）买不上的研究不排除：有的研究要先攒到条件（降价促销 E450 要魔上限 4 万，回蓝 ×6.6），研究少时到不了、填满后能到。2026-10-31 回蓝 60 秒的搜索因此把天使 + 德鲁伊血统 + 矮人显赫验证成 197 万（实际能到 1294 万），各阵营「实测 / 估算」都只有 0.2。数值一律以整局跑为准；给用户的方案只列实际买到的。

研究要游戏显示出来才能买（`Utilities.hasResearchReady`：要研究所、本阵营独特建筑；佣兵还要 Secrets of the Warriors（佣兵独特建筑要 R75 和佣兵研究奖杯），中立立场要 Secrets of the Ancients（只有泰坦 / 德鲁伊 / 无面者独特建筑能解锁），选了显赫阵营要 Secrets of the Underworld）。游戏买研究的函数本身不查这个，所以整局跑只在研究显示出来后才买；整局跑到时间上限研究都没显示出来的阵营（如 R75 前的佣兵、中立佣兵），以及显赫阵营试跑里研究没显示出来的组合，求解时不放研究。2026-10-31 前的版本漏了这条，佣兵局买了实际买不了的研究。

**世系**（Lineage，R60 起每局一个，2026-10-31 加入）：世系要有同阵营的血统（`LineageUpgradeBase.§6!p§` 是血统的运行时 id），所以跟着血统走，不单独穷举。条件是这一局该阵营的皇家贸易令满 400 次（`Formulas.§6!d§`，泰坦 / 德鲁伊 / 无面者世系要另外两个阵营各 400 次），并且不能和所选阵营、显赫阵营相同。第一次选不花钱，等级是永久的。整局跑选完血统后每秒试一次 `Game.buyUpgrade`（世系不查可见性，选时打开 `LineageUpgradePopup` 的标记），选上就记下；估算时直接设 `Formulas.§3"§`。修正前从不选世系，亡灵世系 15 级时助手 ×3.9，结果整体偏低。

**龙族显赫的顺序**：龙族显赫不要求研究数为 0（`DragonFaction01.visible`，要泰坦 / 德鲁伊 / 无面者的第三个条约和驯龙师奖杯），但选了以后没有 Secrets of the Underworld，研究既不显示也买不了（`Game.buyUpgrade`），所以整局跑等研究买完再选（`rg_goal.LATE_PRESTIGE`）。矮人、卓尔仍在研究之前选。可行性试跑带上这个阵营自己的研究（不买研究攒不出第三个条约）；验证时估算方案研究太少、选不上龙族的，先补满研究格再跑。估算也给显赫阵营放上友好协定和联盟，「龙裔」（×2.7）等龙族升级才看得见。

整局跑时佣兵升级按模板顺序优先：前面的还在攒某种阵营币，后面要花同一种币的先等着（否则便宜的次要升级把币花掉，重要的一直攒不够——实测会从 184 万掉到 112 万）。

### 4. 结构之间
- 阵营单位：9 个基础阵营（立场固定）+ 三种立场的佣兵。每个单位：在存档状态上求一版 → 整局跑 → 在它跑出来的状态上再求一版 → 整局跑，得到**这个阵营自己的状态**；在上面估算所有血统 × 显赫阵营。
- 显赫阵营能不能选用实际试跑判断（只选结构、不买研究，规定时间内选不上就不考虑）：它要本阵营联盟、考古 / 驯龙师奖杯，还要花阵营币（矮人条约 2500 矮人币），而且要在买研究之前选——光看条件看不出要多久。
- 每个单位先完整闭环验证自己估算最好的一套，得到这个单位的「实测 / 估算」系数（失败就验证下一套，直到每个单位都有实测）。
- 其余组合：估算 × 本单位系数 × 1.2 仍低于已验证最好的，不可能更好，跳过；其余按可能值从高到低验证。
- 「最快达到」：用时和数值不能直接比，不做数值剪枝，每个单位多验证可能值最高的两套。

并行：3 个低于正常优先级的子进程（`rg_goal.WORKERS`，开 12 个时用户电脑卡死过）。子进程另开线程等父进程（环境变量 `RGA_PARENT_PID`），关掉程序就立即退出（`rg_goal.exit_with_parent`）；以前一整局没跑完时看不到父进程已关，会留在后台继续算，打包版还会弹「Failed to remove temporary directory」。

## 计算引擎（2026-10-31 起默认原生）

整局跑（`Runner.run`）默认用原生（C++）引擎：游戏代码转写成 C++，和 Python 版逐 tick 结果相同。实测同一存档：整局跑 60 秒 18.65 秒 → 0.14 秒，300 秒的佣兵局 42.8 秒 → 0.37 秒；一次完整搜索（回魔，300 秒，12 个阵营单位）18～26 秒。`RGA_NATIVE=0` 改回 Python 版。做法和验证见 `资料/C++引擎设计（20261031）.md`。

## 界面（2026-10-31 重构）

- 设置条：目标、方式（最快达到 / 数值最高）、目标值、时间、要求能用的法术。
- 计算中：左边是星图——中间显示当前最好（数字从旧值滚到新值），外圈 12 个阵营；每个计算进程一条流动的光束连到它正在算的阵营，验证过的阵营按成绩变大，第一名带转动的虚线圈；进度环按三个阶段的大致耗时加权。右边是阶段（启动 → 各阵营跑状态 → 每阵营验证一套 → 验证其余）、已验证 / 跳过 / 用时和滚动日志。
- 结果：「各阵营最好」条形图（点一行只看这个阵营）+ 排行（全部验证过的，按名次；可按立场、阵营、血统筛；点开看曲线、每项贡献、佣兵 / 研究模板，可复制或存进游戏）。
- 不跳：后台每条结果带稳定编号 `id`（只追加、不再变），`goal_status` 带 `known` 只发界面还没有的；界面每条结果一个固定元素，只调顺序、名次和相对条，换位置用 FLIP 动画平滑移过去，展开的详情不重画。
- 后台交给界面的：`phase`、`running`（每个进程正在算的结构，来自 `Pool.running`）、`units`（`Optimize.unit_stats`：每个阵营的状态、组合数、验证数、最好的一套）、`entries`、`log_total`。

## 验证（用户存档 A1 R60，2026-10-31，目标「第 5 分钟魔上限最高」）

- **结果（修正研究显示规则后，2026-10-31 重跑）**：中立德鲁伊 + 无面者血统，不选显赫阵营，研究 S30,C330,D270,S475,S400,S200,S105,C475,C400,C340,C425,D1275,D1375,D450,D300,E290,E450,E330,E150,E200,E400,A250,A550,A400,A150,A1325,A105,W350,W400,W1375,W200,W250——整局 **39.5 万**。主要贡献：D270 ×1.92、S400 ×1.40（经回魔 / 产出填空格）、C330 ×1.25、无面者血统 ×1.15、S475 ×1.13。用时 44 分钟，12 个单位验证 24 套全部跑成，跳过 210 套。
- 各单位整局最好：中立德鲁伊 39.5 万、邪恶亡灵 27.7 万、邪恶恶魔 24.5 万、善良仙灵 23.8 万（显赫矮人）、中立无面者 21 万、中立泰坦 20.4 万、善良精灵 20.4 万、邪恶地精 19 万、善良天使 18.2 万；佣兵不能研究，中立 7.9 万、善良 3.5 万、邪恶 1.8 万。善良三族的实测 / 估算系数只有 0.5 左右（估算偏高），其余 1.0～2.6。
- **作废的旧结果**：修正前（中立佣兵 + 无面者血统 207 万、仙灵 109 万等）买了游戏不显示的研究——R75 前的佣兵研究、别的阵营专属的研究——数值虚高，不能用。下面的穷举对照只检验求解器在同一状态上的组合搜索，不受影响；置顶 build 对照和剪枝抽查是在旧规则下做的，要重做。
- **穷举对照**：同一个状态上，求解器和对相关研究 × 佣兵升级全部合法组合穷举（佣兵 4096 种、仙灵 64 种）的最大值完全一致。

## 已知限制

- 估算不含「填空格」的驱动价值（太慢），所以各单位的实测 / 估算系数在 0.5～2.6（善良三族估算偏高，其余偏低）；剪枝用的是本单位自己的系数加 20% 余量，不是证明，是有依据的估计，结果里写明跳过多少。
- 佣兵的 MA 格、佣兵法术、联合合同还没纳入。
- 只模拟玩家按「全部购买」，自动施法沿用退位前的设置；手动施法、点击、挑战、活动不在内。
- 「最快达到」模式还没做完整验证。
