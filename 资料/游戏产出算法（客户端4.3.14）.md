## 客户端显示的总产出

```
总产出/秒 = 建筑产出/秒 + 助手收入/秒
建筑产出/秒 = Core.getProductionPerSecondReal()
助手收入/秒 = Core.getAssistantsMultiplier()
             × Core.getAssistantResourcePerClick()
             × Core.getAssistantsNum()
```

`getAssistantResourcePerClick()` 使用 `getResourcePerClickReal(true)`；玩家点击使用另一种参数口径。建筑占比与总收入占比也要区分：助手没有对应一栋建筑。

源码证据：客户端底栏 `§"#§/§=!R§.as` 的 `§6z§()` 直接把两项相加；统计 `§4&§/§1F§.as` 的 `§!!G§()` 分开计算两项；`Game.onTreasureClick()` 的助手分支按同样公式入账。此前约 1700 倍的差距主要是漏加助手收入，已修复 `脚本/rg_sim.py` 的报告口径。

即时试算入口：`脚本/rg_growth.py`。它调用原游戏的购买和施法函数后清缓存重算，只在内存副本上操作；尚不提供持续自动建造和自动施法的未来收益预测。

## 产出的计算顺序（`getProductionPerTickReal`）

1. 每栋建筑的产出 `getResourcePerTick(建筑)` 相加，得到基础总产出。
2. 一组乘区。每个乘区内：拥有某升级（有的还带条件）就乘 `1 + 0.01 × 该升级的 getProductionMultiplier()`，同一乘区里的项互相相乘。
3. 乘区分档，每档最后过 `applyAscensionMultiplier(乘区, n)`：Ascension 次数 ≥ n 时，乘区变成 `乘区 ^ 0.1^(Ascension − (n−1))`。第一批是 1～5 档（本次提取 61 / 6 / 7 / 3 / 9 项）。
4. 另一批乘区（第二批）在 Ascension ≥ 4 时三档都按第 5 档计（`A ≥ 4 ? 5 : n`）。
5. 之后依次乘：宝石加成、RE（`getExchangeMultiplier`）、事件加成、部分法术效果（`applySpellMultiplier`）、几个特定升级（再过一次 Ascension 惩罚）。
6. 结果为 NaN 或负数时返回 0。

## 单个升级/研究的公式

每个升级、研究、法术、阵营类都实现同一组方法：`getProductionMultiplier`、`getBuildingMultiplier`、`getManaRegenMultiplier`、`getMaxManaMultiplier`、`getFCCChanceMultiplier`、`getOfflineMultiplier`、`getClickMultiplier`、`getGemMultiplier`、`getExchangeBonus`、`getAssistantsNumMultiplier` 等（各有对应的 `…Bonus`），公式在 `build/game-effects.json`（794 个类、969 个方法）。

## 建筑的基础产出（`getResourcePerTick`，每栋建筑单独算）

对象：`Game` 是游戏状态类（混淆名 8G，80 个有真名的方法/属性，如 `hasUpgrade`、`hasSpellActive`、`hasTrophy`、`getBuildingNum`、`getUpgradeTypeNum`、`ascension`、`reincarnation`），`Stats` 是统计/判定辅助类（混淆名 &c，159 个，如 `hasBloodline`、`hasChallenge`、`hasSet`、`hasLineage`、`hasUnique`、`getFactionCoinTotal`、`getExcavation`、`getManaProduced`、`getTimeStat`、`getBuildingNumber`、`getAllSpellCastStat`），`Core` 是核心计算类（混淆名 #!!）。读起来像 `Game.hasUpgrade(U<Bloodstream>.id)`，对照版在 `build/game-core.readable.as`（`脚本/readable_core.py` 生成）。

单栋建筑的产出 = 基础值 × 拥有数量 × 若干乘区，顺序是：

1. **基础值**（每 tick）：建筑自带值（见下表），再加上某些升级/血统/UB 给的固定加成（如 Dwarven Bloodline：`ln(1+考古深度)^1.75 × 10^((1.25×阶数)^0.75) / 30`；Goblin Bank 给 Witch Conclave 加固定值；Hall of Legends 的基础值改为「每个奖杯 × 已拥有奖杯数」）。部分升级再把整个基础值乘 `1 + 0.01 × 加成`。
2. **乘以拥有数量**。
3. **第 1 档乘区**（过 `applyAscensionMultiplier(·,1)`）：这一档项最多，包括建筑自带的升级类乘区（"Production" 组里前 19 个）、各阵营/立场升级、奖杯（Hall of Legends 系）、各种按阶数 `12 − 阶` 或建筑数量的特殊项。
4. 第 2～5 档乘区，每档一个 `applyAscensionMultiplier(·,n)`；Ascension ≥ 4 时规则换成另一套（三档合并按第 5 档计）。
5. 最后若干与特定建筑/阶数相关的项（按建筑 id 或阶数判断），结果 NaN 或负数返回 0。

建筑表（`build/buildings.json`；产出 = 表中值 × 30 = 每秒，价格是基础价）：

| 立场(`,!Y`) | 阶 | 建筑 | 基础价 | 每 tick 产出 |
|---|---|---|---|---|
| 无 | 1–3 | Farm / Inn / Blacksmith | 10 / 125 / 600 | 0.0667 / 0.2 / 0.667 |
| 善 | 4–10 | Warrior Barracks / Knights Joust / Wizard Tower / Cathedral / Citadel / Royal Castle / Heaven's Gate | 1800 … 3.2e9 | 2.17 … 40000 |
| 恶 | 4–10 | Slave Pen / Orcish Arena / Witch Conclave / Dark Temple / Necropolis / Evil Fortress / Hell Portal | 同上 | 同上 |
| 中立阵营(3) | 4–10 | Deep Mine / Stone Pillars / Alchemist Lab / Monastery / Labyrinth / Iron Stronghold / Ancient Pyramid | 同上 | 同上 |
| — | 11 | Hall of Legends | 2e11 | 按奖杯数 |

各阶基础价和产出善/恶/中立三套完全相同：4 阶 1800 / 2.167，5 阶 5600 / 6.667，6 阶 38000 / 21.667，7 阶 442000 / 66.667，8 阶 7.3e6 / 283.3，9 阶 1.45e8 / 3333.3，10 阶 3.2e9 / 40000。

建筑价格：买第 k～k+n 栋的总价 = `floor(基础价 × (1 − r^(k+n)) / (1 − r)) − floor(基础价 × (1 − r^k) / (1 − r))`（`getSingleBuildingCost`，r 是涨价倍率，由 `getBuildingCostReal` 结合各种降价升级算出，还没梳理）。

## 混淆字段的含义（用存档写入顺序 `Game.save()` 对社区库 `savecodec2.js` 的字段名得到）

游戏存档是按固定顺序写字节的，把 `save()` 里依次写出的字段和社区编辑器库读档的字段名按位置对上，就知道每个混淆字段是什么。已对上的：

- **建筑**：`6!Z` = id，`!a` = 当前数量(q)，`8!` = 本局累计建造(t)，`2Z` = 本局最大(m)，`[]` = 本R累计(r)，`;!1` = 历史最大(e)。（产出公式里的「拥有数量」就是 `!a`。）
- **升级/研究**：`6!Z` = id，`<!7` = 已购买(u1)，`!!`` = u2，`3!c` = u3，另有随机状态。
- **法术**：`6!Z` = id，`'!X` = 已激活 tick 数(t)，`3A` = 自动施法(a)，`#!B/5!H/8#` = 三种自动施法优先级，`` `r `` = 激活的层级，`2-/5!L/#y` = 本局/本R/历史施放次数，`?j/<q/<!G` = 三档激活时间。
- **Game 状态**：`,!Y` = 立场 alignment（0 无，1 善，2 恶，3 中立）；`-!^` = 阵营 faction（0–2 善，3–5 恶，6–8 中立，11 佣兵）；`#3` = **第二阵营** prestigeFaction（9 矮人，10 卓尔，-1 没有；之前误写成「挑战编号」）；`-!x` = 第三阵营 elitePrestigeFaction（13–15）；`9!m` = 第二立场 secondaryAlignment（4 秩序，5 混沌，6 平衡）；`,P` = ascension；`6!R` = 各阵营币数量；`6!-` = 活动资源；`5!V / =y / @w` = 统计值（本局 / 本R内历届 / 所有R），按统计编号索引（如 `Game.5!V[24]` 是交易所相关）；`1!#` = 世系等级；` ![` = 偶然箭头是否开启；`-Q` = 偶然箭头数值；`4P` = 选项数组。
- **Core 上的**：`@#` = 闪电打击目标阶；`#!c` = 奇迹目标阶；`3k` = 奇迹剩余时间；`` `Q `` = 第二血统阵营(bFaction，-1 没有)；`3"` = 世系阵营；`6!r` = 遗物契印；`1"0` = 石心契印；`6!d[]` = 各阵营币对应的皇家贸易令数量。
- `Core.%b[阶]`（不为 0 时才吃某些加成）这类还没对上。

## 其他计算的基础值（从规则表读出）

- 最大法力 `getMaxManaReal`：基础 1000，加上各升级的 `getMaxManaBonus()`，再乘各 `getMaxManaMultiplier()`，取整；NaN 或负数返回 0。
- 回魔 `getManaPerTickReal`：基础 0.0667/tick（= 2/秒），加各升级的 `getManaRegenBonus()/30`，再乘各 `getManaRegenMultiplier()`。
- 点击 `getResourcePerClickReal`：基础 1，Sturdy Treasure +4、Durable Treasure +45、Reinforced Treasure +4950，再按若干乘区。
- 助手 `getAssistantsNumReal`：基础 0，加各升级的 `getAssistantsNumBonus()`，再乘 `getAssistantsNumMultiplier()`，向下取整；`getAssistantsMultiplierReal` 是助手的乘数。
- 皇家贸易令 `getExchangeMultiplier`：统计 24 ≤ 0 时为 1；否则 `(1 + 0.01 × 交易所加成 × Stats.getExchange())^(ascension>0 ? 0.7×交易所基础^0.7 / (1 + 2.5×ln(max(1, ascension))) : 1)`。
- 建筑价格涨价倍率：建筑自带倍率（字段 `,'`）逐个减去降价升级的值（Pixie Dust Fertilizer −0.02 仅 Farm/Inn/Blacksmith、Bartering −0.02 仅 Farm、Oversized Legends −0.01 仅 Hall of Legends、Expert Masonry −0.01、哥布林血统 −0.01、Gray Friday −0.02、Discount 按自身值、Bribing −0.01 仅独特建筑、Lousy Architecture −0.01 仅非独特建筑、Titan 血统加 Titan Perk 1 对 1/9/11 阶 −0.02、Biased Architecture 挑战 −0.01 仅 Farm/Inn/Blacksmith 等）；Ascension 1–3 时 `r = 1 + (r−1)/(ascension×5)`。
- 法术时长 `getSpellDuration`：Combo Strike 480、Limited Wish 180、Catalyst 1800、Chaos Madness 600（单位 tick，÷30 是秒），其余按法术基础时长加各升级加成，最后向下取到 30 的整数倍。
- 考古价格 `getExcavationCost`：每级倍率 1.2，上限因子 `1e27^(0.75^ascension)`。

## 让游戏自己的代码算（AS3 → Python 转写，2026-10-27）

规则表丢了函数里的先后顺序，不能直接当计算引擎，所以另做了一个转写器，把反编译出的 AS3 整体转成 Python，用游戏自己的函数算：

1. `ffdec -config autoDeobfuscate=1,simplifyExpressions=1,decompilationTimeoutSingleMethod=90 -export script <目录> RealmGrinderDesktop.swf` 导出 AS3（保留混淆名）。
2. `python 脚本/as2py.py <AS3 目录> build/rg_game.py`：转写 `§…§` 名字用 `S_` 前缀加十六进制转义。界面库（starling、feathers、mx）和联网/平台类（playfab、kongregate 等）不转写，运行时当「桩」（`脚本/as_runtime.py`：任何调用都返回自己、当作假值）。82826 行 Python，1800 多个文件里 29 个解析失败（都是资源内嵌、翻译函数，不影响计算）。
3. `python 脚本/rg_sim.py build/rg_game.py`：建好游戏对象（`Game.initialize()`：25 栋建筑、2058 个升级），读本机存档（`realm-grinder.sol` 里 `save` 字符串，经游戏自己的解码函数 base64 → zlib → 异或 → CRC 校验），再调游戏自己的 `getProductionPerSecondReal` 等函数，输出产出、魔力、回魔、点击、助手、FC 概率、各建筑产出等。

转写时处理的 AS3 语义：实例字段的常量初值是槽默认值（不在构造函数里执行，子类先赋值再 `super()` 不会被覆盖）、静态 getter 不被子类继承（元类上的 `StaticProp`）、返回类型 `int/uint` 要转换（CRC 校验靠这个）、`%` 取模和 `/`、`int()` 的 32 位回绕、带标签的 break/continue、switch 落空、`Math.pow` 溢出等。

第一次跑出的结果（存档读到的状态：Farm 3718、Inn 3633、Blacksmith 3580、430 个升级；游戏还在自动买建筑，每次读到的存档会略有不同）：产出 ≈ 4.35e26 / 秒，最大魔力 7885，回魔 ≈ 1044 / 秒，每次点击 ≈ 3.7e25，助手 1795，FC 概率 1138，皇家贸易令倍率 1，宝石倍率 11.8，红宝石加成 100，奖杯数 1099.8。**这些数还没有和游戏界面对过**，对不对要靠对比验证。
