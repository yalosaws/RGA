# 计算性能与客户端时间推进核对（2026-10-28）

结论：已修正当前试算反复初始化游戏、反复使缓存失效的问题。固定存档下首次“购买 10 栋农场”由约 2173 毫秒降至约 103 毫秒，约 21 倍；对同一存档重复同一动作复用结果。资源、动作成功状态和前后数值与优化前严格一致。连续增长循环尚未接到界面。

## 客户端实际上怎样推进

依据实际安装版的 `Game.onEnterFrame`、`Game.advanceTicks`、`Core` 缓存入口，已同时查看 AS3 和原始 pcode。检查对象是 `build/installed-as3-deobf/scripts` 与 `build/installed-pcode/scripts`，不是旧汉化包。

1. `onEnterFrame` 累积真实经过时间，每个逻辑 tick 是 `1/30` 秒；单次积压限制为 `1/3` 秒，计算本次需要推进多少 tick，再交给 `advanceTicks`。
2. `advanceTicks` 每次处理魔力回复和法术推进、建筑收益；每累计 30 tick 进入整秒分支，结算助手、检查奖杯与升级、更新若干统计。助手结算与建筑逐 tick 收入并非同一条路径。
3. 缓存有明确的失效标志。`getProductionPerTick` 在失效时才调用完整公式 `getProductionPerTickReal`；最大魔力、回魔和助手单次收益也有对应缓存。购买和施法按客户端条件使缓存失效。
4. `advanceTicks` 还会周期性使部分缓存失效。源码中相关计数器按推进调用次数增加，达到 150 时触发；平稳每次推进 1 tick 时通常约为 5 秒。不能把所有分支都误当成只按传入 tick 数线性累加。
5. 离线 `timeWarp` 是另一套逻辑，包含法术与离线加成规则；不能作为精确的在线逐 tick 循环替代。

所以连续模拟需要接入原有时间、整秒和法术事件处理，并维持与客户端一致的状态更新顺序，不能只把当前总产出乘经过时间。本文的性能优化没有声称连续模拟已经完成。

## 原实现的主要耗时

旧的每次试算都会读取并编译约 4.7 MB 的转写模块、执行类定义和静态初始化、创建全部升级/奖杯等对象、载入存档，然后才执行购买。性能分析中，初始化占据绝大部分时间。常规读取数值还无条件调用 `invalidateAllCache`，之后再调用完整计算入口，缓存无法充分复用。

## 已实施的修改

- 模块代码使用 Python 校验源码哈希的字节码缓存，并在工作进程中复用不可变代码对象；不同存档仍使用独立游戏状态。
- 同一份已载入存档保留一个内存检查点。试算前后恢复对象、容器、静态字段、ByteArray 游标、内存 SharedObject 与随机数位置；异常时也在 `finally` 中恢复，不再每次重建整个游戏。
- 程序读取使用客户端已有的缓存入口；动作入口使缓存失效后再计算一次。全量重算路径继续保留，供独立对照核查。
- 同一存档下重复的动作、说明查询及完全相同的载入请求复用结果。换存档或时间上下文后清除缓存；无效数量等输入在命中结果缓存前仍须校验。
- 查询也在状态事务内进行，防止描述方法或缓存更新影响随后的试算。

## 征税为什么能大量自动施放

实际安装客户端 `Game.useSpell` 在自动模式、目标为征税、没有购买“圆桌会议”时，计算 `floor(当前魔力 / 本次费用)`，一次扣除对应费用、增加施放次数，再调用一次 `onEffect(次数)`。征税的主要资源收入乘以传入次数；复制效果也按次数整体追加，而不是把每次复制都单独重新执行一次完整公式。尚未获得特定奖杯时仍有少量逐次记录分支，不能说整个方法完全没有循环。

这条路径在 `Game.autocast` 中以自动参数调用；`advanceTicks` 的整秒分支触发自动施法。因此，显示很高的征税次数，并不意味着每秒进行了同样多次完整产出重算。持续模拟应调用客户端的这条批量入口，不能把大量手动单次调用当作等价替代；中途统计和随机数状态的变化可能影响结果。

`benchmark_tax.py` 在相同冻结存档上测得：

- 单次手动征税：消耗 160 魔力，因复制效果增加 2 次施法统计，约 175 ms。
- 一次自动批量调用：消耗 20480 魔力，相当于 128 次基础费用，含复制共增加 256 次统计，也约 174 ms。
- 16 次手动调用：约 2763 ms；这说明保留客户端的批量处理方式对连续模拟很重要。
- 当前完整单次试算：约 284 ms，其中施法阶段约 178 ms，施法后生成数值汇总约 91 ms，其余为状态恢复等开销。不是每一次游戏内征税都会承担完整试算报告的成本。

这些毫秒数是我们的 Python 转写引擎内部耗时，不是对原游戏施法耗时的测量。转写层仍有大量动态类型与对象访问开销。上一节“重复试算约 0.02 ms”表示完全相同输入的结果缓存，不能拿来代表状态持续变化时的真实施法速度。完整记录在 `build/tax-paths.json`，可用 `python -X utf8 scripts/benchmark_tax.py` 重测。
