# build 求解重构方案与机制核对（2026-11-01）

本文记录前一轮的客户端机制全集索引、固定存档实验和重构设计。后续已实现并打包其中的研究分支交叉优化，快速深度实测回魔最好值提高 2.64%、魔上限提高 2.23%，见 [build搜索实测对照（20261101）](build搜索实测对照（20261101）.md)。后续又完成独立搜索主线替换与机制提案模型编译，见 [build求解器重构与验收](build求解器重构与验收（20261101）.md)。下文的激活效果编译器和单局物理计算加速仍属于设计，本次没有把它们冒充已完成。

建议采用：**完整规则编译、保留真实事件顺序的快速精确评估、按增长链和解锁条件联合搜索。** 不再让一个借来的终态上的单项静态增益，决定一套 build 有没有资格进入搜索。

## 1. 核对范围与证据

权威输入是当前安装客户端的可读 AS3：`build/installed-as3-named/scripts`。现有中文描述和旧依赖图用于对照，不作为公式和购买规则的替代。

新增 `scripts/rg_mechanics_audit.py`，生成：

- `build/mechanics-audit/mechanics.json`：每个类的继承、源码位置、原文件 SHA256、方法全文、调用和属性读取、表达式 AST、可能写状态的语句、未解析项。
- `build/mechanics-audit/methods.md`：升级、研究、法术、建筑的规则原文索引。
- `build/mechanics-audit/research-brief.txt`：264 项具体研究的已有中文公式对照。
- `build/mechanics-audit/probe.json`：固定存档的真实引擎实验，脚本为 `scripts/rg_mechanics_probe.py`。

索引到 2458 个类、14630 个方法；其中普通升级类 986 个、研究类 265 个（含基类，264 个具体研究全部找到）、法术类 33 个、建筑类 26 个。数量含相应基类。游戏升级、研究、法术的 1235 个 `get…` 数值方法中，1191 个可解析成表达式，44 个是多语句或其他不能直接按单表达式处理的情况，原文全部保留。另有费用、条件、购买回调、更新和解锁规则，也保留方法全文。

这是**完整的源码索引和保守语法审计**，不是已经证明完整的公式执行器。动态分派、参数别名和状态读写还需要编译器级的数据流分析；不能把 1191 个表达式“解析成功”说成游戏语义已经全部验证。24 个未按类索引的文件主要是界面库和顶层辅助函数，清单在 JSON 中；14 个重名方法也显式列出，没有覆盖或静默丢弃。

逐项核对了 264 项研究的公式对照、原有 344 项阵营机制目录，并补查执政官、巨灵、永衡族、契印/套装、研究基类、血统/世系基类、佣兵合同、挑战奖励、法术更新和所有游戏数值 `get…` 中的 44 个复杂或未直接解析的方法。对于作用写在其他类的研究，追到实际的 `Utilities`、`Formulas`、`Bloodstream` 和法术实现。

固定输入 SHA256：`97314afa8d80b5192db18fb862119c963386771ccd27361159936023322b7cb1`。副本在 `build/mechanics-audit/input.sol`；实验只读副本，不写原游戏存档。

## 2. 已查明的结构性问题

### 2.1 静态试算会留下虚拟方案的历史记录

`Formulas.getMaxManaReal` 第 3118 行写本局最高魔上限；`getManaPerTickReal` 第 3551 行写最高回魔统计；`getAssistantsNumReal` 第 4110 行写最高助手统计。最高助手记录还在部分临时法术加成之前写入，不能用最终显示助手数直接代替它。回魔函数和最高回魔统计使用每 tick 单位，界面每秒回魔另乘 30。

现有 `Planner.save/restore` 只保留部分拥有标记、立场/阵营和世系字段，没有恢复这些历史记录。

固定存档实测：合法方案跑到第 60 秒，最高魔上限记录为 **649566**。用现有 Planner 试一个超额研究组合后恢复原方案，该记录仍变成 **86562964**。虚拟组合的结果被留在了真实参考状态里。

此外，`sim.refresh()` 调用 `Game.invalidateAllCache`。其中 `invalidateSpellCache` 会更新法术的缓存时长，并调用收税的 `onReset`；它不只是把几位缓存标记设为失效。

影响范围：静态候选选择、多时刻切换标记的探测、静态贡献解释可能受影响。**这一实验没有证明结果榜上所有整局数值都错了**；不带探测的 `Runner.run` 会先恢复完整基准快照。应分别检验参考估值污染和最终精确回放。

新实现必须支持独立、可嵌套的完整世界检查点，或真正无副作用的公式评估。现有原生 `snapshot()` 只有一个全局快照槽，不能直接在静态试算中调用它覆盖 Runner 的基准快照。

### 2.2 现有候选图漏的是规则依赖，不只是数值链长度

对当前 `Graph.relevant` 实查，所有目标的直接候选都没有 A400、S400、E1325；D5875、E3300、F5750、F11500、E13500 这类规则修改也不在其中。

- A400：改变 `Utilities.hasBloodline`。没有显赫/后续阵营时可提供基础阵营血统；有显赫阵营后提供的额外血统会随结构变化。它不是一项固定的“产出乘数”。
- S400：按本 R 最高施法次数，提高公式看到的有效遗物数；然后影响 D270、S475 等按遗物计算的魔上限、回魔和其他效果。它**不直接改有效魔上限**。
- E1325：降低皇家贸易令的价格增长系数，改变之后能买多少次贸易令以及何时越过世系门槛。
- D5875、F5750、F11500：分别提供额外血统、联邦、契印效果，要读规则分派，不能找不到自己的数值函数就当成没有效果。
- E3300：改变独特建筑的启用规则。
- E13500：启用一组世系，并限制部分世系效果的等级，需要同时表示收益和限制。

不设深度上限的语法调用追踪，可以沿 `Utilities.getArtifact` 找回 S400，沿 `Utilities.hasBloodline` 找回 A400 和 D5875。它仍找不出所有增长关系：E1325 需要从贸易令购买成本的入口追，不能只从终点回魔函数追。`Game.buyUpgrade` 对参数对象调用 `onPurchase` 的动态分派，也不能只靠静态的 `Class.method()` 正则解析。

**候选依赖至少要有数值、规则/条件、购买状态转换三种边，且闭包不能固定两层。** 未证明无影响的项，应保留或走精确回退。

### 2.3 “六分支、固定格数”不是完整的研究约束

`ResearchUpgrade.capReached`：

- A0/A1 按研究格数约束。
- A2 对本阵营/显赫阵营专属研究有免占格规则；执政官血统可随本局时间增加格数。
- A3 起按已花研究点数和预算比较，不再是简单的数量上限。
- 第七分支 Forbidden 的编号为 6，预算有单独入口；当前 Planner 的 `range(6)` 覆盖不到。
- 预算还受血统、契印、设施、佣兵法术/联邦合同等影响。

同理，结构选择不能长期写死为 9 个基础阵营、12 个血统和一层显赫。后续阵营、第二立场、额外血统/世系/契印、佣兵法术与合同都应由客户端规则和存档进度驱动。

## 3. 增长到底怎样发生

### 3.1 一个公式读取的“量”必须带完整语义

至少区分：

- 显示魔上限与其他公式读取的有效魔上限；显示助手与有效助手；实际遗物与有效遗物。
- 本局、本 R、本 R 之前几局、之前各 R、单局最高值。
- 包含/排除临时法术、包含/排除读数放大、离线/在线、特定建筑/法术。
- 当前金币、累计获得金币、最高金币；当前阵营币和累计阵营币。

例如 `Utilities.getManaProduced` 三个参数会改变统计范围和是否应用德鲁伊特权 5、时流涌动等放大。不能都压成一个 `mana_produced` 节点。游戏依赖缓存、参数分支和执行顺序避免部分自引用；不能把看到的环直接交给一个通用不动点迭代器。

### 3.2 加法、乘法和升华分区

常见形状可以写成：

`y = (基础值 + Σ 加法项) × Π (1 + 百分比项/100)`

产出还要先算各建筑、分乘区应用升华折算、再组合宝石/贸易令/法术等效果。`applyAscensionMultiplier(v,k)` 在相应升华后取 `v^(0.1^(A-k+1))`，不能把处在不同乘区的 1000% 当成等值。

有用的局部判断是实际弹性，而非只读幂次：

- 对加法项 `a*x^p`，它对 `y` 的弹性还要乘这一项占加法底数的比例。
- 对乘数 `1+c*x^p`，弹性是 `p*c*x^p/(1+c*x^p)`。
- 对 `(ln(1+x))^k`，弹性为 `k*x/((1+x)*ln(1+x))`，再乘相应份额。
- 再经过升华分区，要继续乘该分区的折算指数。

弹性适合指示联合搜索方向；有门槛、取整、取模、数位和、随机切换的地方不能靠导数判断。

### 3.3 实际产生魔力受魔力槽和消耗节奏限制

设 `m` 为槽内魔力、`M` 为上限、`r` 为每秒回魔。`Game.advanceTicks` 每 tick 的基本补入量为：

`q = min(M-m, r/30)`

`累计产生魔力 += q；m += q`

随后到整秒才进行自动施法，施法再扣魔力，法术更新可能又改变上限。圆桌会议等还有额外的统计修改，要保留其专属代码。

因此通常不能写 `累计产生魔力 = ∫r dt`。持续收税并每秒消耗一次时，在回魔已经远超魔上限的区间，实际生成速率常接近每秒一个魔力槽的容量。提高回魔可以继续提高“回魔”目标，却不一定继续加快靠累计魔力成长的项。

固定存档、德鲁伊 + 德鲁伊血统 + 龙族显赫的第 60 秒：

- 显示每秒回魔：约 `1.4847e10`。
- 魔上限：`11041600`。
- 第 59→60 秒实际增加的累计魔力：`11017919`。

把此时回魔当成实际生成速率，会高估约三数量级。观测版与未插入观测的该次精确回放终点相同。

### 3.4 阵营币、贸易令和收税形成另一套增长链

阵营币收入来自助手点击、自动点击、精灵幸运、收税附带奖励等。秘密交易就同时读有效助手、收税奖励和阵营币获取率的 1.25 次幂；收税次数又受实际可消耗魔力、消耗、自动施法频率和复制次数限制。

贸易令和建筑按几何级数付费。便于理解的连续近似是 `数量 ≈ ln(累计可花资源)/ln(价格增长系数)`。它们的数量对金币增长相对迟缓，却可能对价格增长系数十分敏感；降价研究绝不是一个可直接丢掉的“没有当场目标贡献”的项。

而且花币会减少其他购买的余额。多买贸易令可能推迟龙族条约，多买便宜佣兵升级可能挡住重要升级，当前金币下降还会影响按当前金币计算的效果。这个系统不满足“每项越多，所有以后状态都更好”的一般单调性。

### 3.5 法术、门槛、历史最高值都是真实状态

- 龙息按自身 `Rand` 流选择颜色，蓝色的基础回魔乘数是 ×3；多阶可选多种颜色，颜色并非每秒独立抽样。
- 雷击目标、大平衡每 15 tick 重分配、脑波每 tick 更新、临时助手、施法阶层和时长都要保留独立状态。
- 部分升级是读数放大器；部分研究是启用另一条规则的开关。
- E450 的魔上限 40000 是购买门槛；世系要贸易令数量；不同显赫阵营和研究有不同购买顺序。
- 历史最高值是记忆。高一次就能永久改变本局后续公式，不能用时间平均替代。
- 无面者部分效果、联邦、图书馆、烈焰之渊等存在取模、奇偶或数位公式，会随增长跳变甚至变差。

这些都要求将 build 表示为**选择 + 执行策略 + 状态轨迹**，而非一个升级集合。

## 4. 哪种 build 更好的统一判据

先固定永久进度、合法历史统计、存档时钟、所有游戏随机流、购买/施法策略和目标口径。所有方案从同一个合法退位起点独立计算。

确定性口径：

- 数值最高：`J(b)=目标值(执行 b 到 T 的完整状态)`。
- 最快达到：`τ(b)=第一次达到目标的合法观察时刻`；未达到的另外记录终点值，不伪造成已达到。

必须写明时间分辨率；现有回魔等每秒检查、产出/宝石每五秒检查的“最快”不是连续时间的精确到达时刻。新的精确评估需在相关事件时刻检查，必要时定位到 tick。

随机效果有两种不同问题：

1. 当前存档实际会跑成什么：保留存档中的全部随机流，给可复现的终点值。
2. 这套 build 多次玩通常好不好：对完整随机场景分别回放，比较期望、分位数和达到概率。

二者应分开显示，不能偷偷把瞬时目标换成平均回魔。对场景回放也不能只改 Python 的 `random.seed`：龙息、雷击等还有各自的游戏 `Rand` 对象。也不能先把龙息颜色替换成平均乘数后当成期望结果，因为非线性增长和门槛下 `E[f(X)]` 一般不等于 `f(E[X])`。

## 5. 推荐的新架构

### 5.1 规则编译层：一份来源，完整覆盖

基于现有 AS3 解析器，而不是再写一套函数名正则白名单。生成带参数、统计范围和读写集合的中间表示：

1. 纯数值表达式及原始计算顺序。
2. 条件、可见性、能否购买、互斥、研究格数/预算、价格和货币预留。
3. 购买、解锁、法术开始/结束/升级、每 tick/秒更新等状态转换。
4. 启用额外血统、联邦、契印、独特建筑的规则分派。
5. 查询时写最高值、缓存和派生状态的明确语义。

节点必须包含方法参数和读取口径；动态分派要按类继承解析。未支持的代码块使用现有精确引擎回退，并明确标记覆盖状态。不能默认为零，也不能从候选里删除。

依赖图同时跟踪效果、门槛和状态转换，迭代到闭包。用强连通分量和条件超边识别需要联合处理的选择，而不凭相隔两层就截断。

### 5.2 快速精确评估层：减少每次重算的成本

当前一局 60 秒实测约 0.14～0.16 秒，300 秒约 0.72～0.84 秒。这里不能凭设计就声称已经快几十倍。

具体加速路径：

- 预绑定升级 ID、对象字段和方法；用连续的拥有标记和已激活效果表，避免每次重算重新走大量动态查找。
- 每个公式按源码顺序保存有效项；未拥有且无其他启用路径的项不进入这次执行列表。购买或结构变化时更新列表。
- 对确定不变的永久输入和分支做局部求值；对参数不同的公式保留不同版本。
- 用准确的读写依赖决定何时重算，同时保留客户端原有缓存刷新语义。
- 条件、法术状态、最高值写入、取整、浮点运算顺序、随机抽取顺序保持一致。
- 第一步仍按原始 tick 顺序推进。只有某段无中间事件、且批量转移与逐 tick 等价得到证明时，才允许合并；不把“事件驱动”当作跳过 tick 的许可。

最费钱的通常是清缓存后的全量公式重算，不是那几个时间循环。先减少数千次重复条件查询，再讨论更激进的时间跳跃。

静态反事实需要事务：捕获完整状态 → 对另一方案计算 → 回滚全部物理状态、历史记录、法术内部字段、随机流、缓存、时钟和新对象。公式纯化也应把最高值更新做成显式输出，再只在真实轨迹执行时提交，保留提交顺序。

### 5.3 搜索层：按机制联合求解

每个结构保留多套完整可执行的候选：开局收入优先、实际魔力生成优先、法术覆盖优先、门槛优先、终点目标优先。它们是不同增长路线，不能只留当下静态分数最高的一套。

每轮搜索做三类确定的联合修改：

- **增长链模块**：例如有效遗物 → D270/S475 → 魔上限 → 德鲁伊血统回魔；魔上限 → A120 助手 → W205 回魔；阵营币收入 → 贸易令 → 助手/世系 → 阵营币收入。一起决定相应分支的取舍。
- **门槛包**：研究本体、够到购买条件的辅助项、腾出的格数/预算和购买顺序一起求。明确试“牺牲一点当前分数换来后续解锁”的路径。
- **规则模块**：血统与 A400/D5875、遗物/读数放大与消费者、佣兵法术与预算合同等一起求，不能把没有独立直接增益的开关先删掉。

对一个规模可控的小模块，固定其他选择后穷举合法组合或用有上下界的离散求解；模块过大时用保留多解的束搜索，并记录截断。联合修改按同一份格数、预算、互斥和可达性约束求解，不能把分别合法的几项直接拼起来当成整体合法。

局部弹性、分段增长近似、未来门槛到达时间可以决定先试哪些模块；它们不能决定最终名次。保留不同结构、不同门槛路线和早/晚增长路线，避免只给静态前几名资源。候选缓存包含输入/规则版本、时间、目标、所有随机流、完整选择和实际执行策略；研究顺序会影响行为时也必须进入键。

本次对固定存档做了原顺序、倒序、按代号排序的六次实验，60 秒和 300 秒终点各自相同。**当前存档未复现研究顺序导致的缓存碰撞**；但当前缓存对研究列表排序后合并，而 Runner 按列表顺序购买，通用实现不能未经证明就声明二者等价。

停止时只报告实际达到的搜索覆盖程度。“全部单项检查过”不等于“全局最优”。如果要证明某个小范围最优，报告该范围、完整枚举量或上下界间隙。

### 5.4 保留独立的精确裁判

新评估器与当前未经修改的精确引擎分开。最终入榜方案用原引擎从原始固定快照回放，核对实际买到的项目、购买时间、法术可用性和完整目标轨迹。数值与方案必须来自同一次有效执行。

近似误差小、排名相关高、前几名看起来正常，都不能代替这一步。也不能只拿最终候选回放正确来宣称搜索没有漏掉更好的方案；后者是不同的验收项目。

## 6. 已完成的定量实验

同一固定存档、德鲁伊 + 德鲁伊血统 + 龙族显赫，其余研究相同；下表只改变 A400、S400 是否购买，所有列出的研究均买到。不是对这套研究重新做了全局寻优。

| 研究变化 | 第 60 秒回魔 | 第 300 秒回魔 |
|---|---:|---:|
| 不带 A400、S400 | 7.0186e9 | 1.3033e10 |
| 只带 A400 | 1.2258e10 | 1.3046e10 |
| 只带 S400 | 1.4867e10 | 4.7286e10 |
| 两项都带 | 1.4847e10 | 4.7253e10 |

结论：S400 是重要的间接来源，必须进入机制模型。A400 在这个固定搭配的 60 秒有效，但在 300 秒收益很小；和 S400 同时买还略差于只买 S400。**同一个研究没有脱离其他选择和时间的固定“好坏分数”，把空格全填上也不保证更好。**

同一实验还测了无面者血统，合计 16 组结构/时间/研究开关组合。原始数值、实际生成魔力、魔上限、购买跳过项和耗时都在 `probe.json`。这些只用于验证机制和暴露旧判断的盲区，不代表新搜索器的速度或结果基准。

在第二个独立进程复跑，16 组机制实验、6 组购买顺序实验的全部数值及购买结果逐项一致，观测轨迹和状态污染复现也相同；固定输入哈希不变。两个新脚本通过 Python 语法检查；审计检查确认 264 项研究全部存在、已解析与未解析数值方法总数相符、关键规则依赖闭包能找回上述缺失研究。

## 7. 实施顺序与切换条件

1. **先消除估值污染与覆盖漏洞**：完整事务/纯函数评估；补规则与购买依赖；按客户端提供分支与研究约束。验收候选访问顺序不改变评分、回滚后状态完全相同。
2. **实现激活效果编译器和快速精确评估**：同一存档、同一计划、同一随机流，逐事件与旧引擎对照；任何差异先定位，未支持路径精确回退。
3. **实现联合模块搜索**：用可完全穷举的小问题检验最优值；用固定存档、历史好方案、社区合法模板和旧搜索结果作质量基线。新算法不能靠改变目标口径显得更好。
4. **评测整轮耗时和结果**：各目标、60/300/3600 秒、最快达到/数值最高、不同升华规则、不同法术和购买门槛。速度和质量分开报告，保留失败样本。
5. **程序接入**：结果标明目标口径、规则版本、实际买到的项、回放验证状态和搜索覆盖范围。精确回放失败的方案不能入榜。

必须覆盖的回归用例包括：S400 的有效遗物链、A400 的额外血统随结构切换、E450 门槛、回魔饱和、世系 400 贸易令、龙息颜色与阶层、脑波临时助手、大平衡刷新、历史最高值、A2 免占格、A3 预算和 Forbidden 分支、借用血统/联邦/契印、付费研究和佣兵币预留。

关于“保证结果”：可以要求数值按原逻辑计算、方案可执行、同一输入可复现，并用独立回放验证；**不能把这些保证等同于已经证明找到了整个游戏范围内的全局最优 build。** 后者必须有完整枚举或有效上界证明。新求解器应该明确给出证据范围，不再用“检查过”替代这个证明。
