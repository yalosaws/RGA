# 社区 build 严格评测与对照（2026-11-01）

本轮完成严格模板评测、社区模板购买完整性自检、长时活动上下文修正，以及 60/300/900/1800 秒分别独立搜索的对照。用户明确选择：随机择优继续暂缓。本轮全部结果采用固定随机流，不主动重摇法术、择色或瞄准。

**结论：不能认定求解器已全面超过社区。** 60 秒这一轮明显领先，300/900/1800 秒的独立搜索均明显落后；已找到的 60 秒方案在长时复测时仍然很强，证明长时搜索漏解，而非没有可执行的强方案。

## 输入与口径

- 固定 A1 R60 存档：`build/mechanics-audit/input.sol`，SHA256 `97314afa8d80b5192db18fb862119c963386771ccd27361159936023322b7cb1`；文件内容和时间戳未改变。
- 目标是「第 T 秒的即时总产出/秒」：建筑产出 + 助手收入。它不是累计产币，法术到期或效果变化时允许下降。
- 每个时长独立搜索 240 秒墙钟预算，6 个低优先级进程；已提交的整局和最终复核可以跨过截止点。不以社区模板或其他时长的胜出方案给独立搜索初始化。
- 每 2 秒全部购买；自动施法沿用存档设置；不模拟手动点击、挑战操作、雷击瞄准、龙息择色。社区实玩要求的主动法术操作没有被实现，因此此处不比较完整实玩策略。
- 游戏逐 tick 推进，无粗跑、无落后曲线提前终止。产出目标每 5 秒检查，正常曲线每 10 秒采样。
- `seed=0` 是初始化全局随机源的种子；同时完整恢复游戏各个 `Rand` 对象的状态。游戏的 `Rand` 继承 `PM_PRNG`，不能把所有随机效果都称作 MT19937，也不能把改一个 Python 种子等同于逐个法术重摇。

## 严格入口：缺一项就不给分

入口为 `scripts/rg_evaluate.py:evaluate_template`、命令行 `rg_evaluate.py`，以及程序「构筑辅助 → 评测已有 build」。程序可以选社区模板，再明确核对立场、阵营、血统和显赫；也可手动粘贴研究/佣兵模板。

严格入口不补选结构、不删除项目、不重新解释一份残缺模板的得分。它检查实际结构和拥有状态，以及研究、佣兵升级、`SP:` 法术合同、`MA:` 盟约是否买齐；未知项目、重复项目、互斥或不匹配结构也会报错。提前达标时不依赖 `skipped` 是否为空，而是检查实际购买结果。失败返回 `ok=false`、`validated=false`、`value=null` 和逐项原因；程序显示错误。

底层 `Runner.run` 仍是宽松执行器，供求解器尝试和修复候选。评测外部模板必须走严格入口。`lineage` 仍表示尝试选世系，实际选定项另列，不会把未选到的世系显示为已拥有。

原先执行器遗漏了佣兵模板的 `SP:`。本轮按客户端合同槽位和实际购买函数接入 `SP:`，并接入 A1 的 `MA:` 第 13 格及其圆桌会议/黑暗契约限制。当前 R60 存档上验证了 12 项升级和两个法术合同确实买齐；未来阶段的全部佣兵能力未做端到端验收。

案例：`R60-62 DNTT (prod, e57+)` 必须选龙族显赫。本例五项研究的客户端归属确实为龙族，不应泛化为“所有编号 1000 以上的研究都属于龙族”。未选龙族时五项未买到，严格入口直接拒绝；选龙族后 32 项买齐，第 300 秒为 `3.103475240308911e154`。

缺「地下世界的秘密」的情况也已核对：客户端明确禁止在选显赫后购买研究；相关龙族研究的购买归属又要求龙族。对本例而言，无此秘密时不存在可实现完整模板的购买顺序，不能仅靠改等待顺序解决。原生规则测试验证：同一已解锁研究与资源状态，移除秘密时购买失败，恢复秘密后成功。该规则测试不作为虚构存档的得分发表。

## 3600 秒下降：两种原因，不能强制单调

第一类是真实法术到期：350→355 秒、2835→2840 秒附近，Gem Grinder 与 Spiritual Surge 从生效变成不生效，产出允许骤降。不能为了曲线好看而钳制为历史最高。

第二类是活动上下文缺失。旧模拟从存档恢复了活动编号 7，却未提供活动排期；`Utilities.getExpectedSeason()` 读到空排期返回 0，`Game` 约每 1800 秒核对时清除活动。1805→1810 秒的读数骤降对应 Crucible Of Darkness 等活动加成消失。

本机 `rg-cache.sol` 保存了真实排期：UTC 2026-10-28 13:01 至 2026-11-04 19:59（台北时间结束为 11 月 5 日 03:59），覆盖本次存档时钟及一小时模拟。现在只读提取 `ne/nes/nee`，在基准快照建立前用客户端公开 PlayFab setter 恢复；不修改游戏产出公式，也不改变随机择优口径。设置排期时保持全局随机源状态，避免元数据恢复扰动游戏随机流。

原生 boot 的旧 `event_cache` 参数路径早于静态初始化，本轮通过公开 setter 在载入后恢复排期，避开该路径，无需改动原生二进制。缺失或无法读取排期时明确假定“保存时活动状态保持到本次模拟结束”，界面及结果环境会标注，不再把未知排期解释成活动已结束。

同一 DNTT 固定方案：

- 第 1800 秒：旧/修正后均为 `1.504270267293578e+155`。
- 第 3600 秒：缺排期为 `3.518404733011057e+154`，正确排期为 `5.473442675615834e+157`。
- 1800 秒短局与 3600 秒长局的共同前缀精确一致；带观测与不带观测的结果、整条曲线一致；终点缓存产出与直接公式重算一致；累计产币没有因这次产出下降而减少。

证据：`production-horizon-raw.json` 与 `production-horizon-probe.json`。3600 秒是环境修正和跨时长诊断，未给求解器另做一个 3600 秒独立寻优，不能拿它替代独立搜索对比。
