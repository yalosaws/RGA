## 2. 使用者如何查看和试算

### 2.1 构筑辅助

进入程序的「工具 → 构筑辅助」。

- 可按中文名、英文名、研究代号搜索，也可查找影响同类数值的升级。
- 清单包含 2,059 项升级，含没有统一加成方法、在汇总逻辑中处理的研究。
- 显示说明、拥有状态、可用的自身公式值，以及总产出、建筑产出、助手收入、回魔等汇总值。
- 可试买建筑、升级，或施放一次法术；显示动作前后的资源和数值变化。
- 试算在独立对象中执行，不向游戏输入购买或施法操作，不写回游戏存档。

两种输入来源：

| 操作 | 输入与更新方式 |
|---|---|
| 使用存档计算 | 使用“我的存档”同一份导出串和时间；新存档到来后清除旧结果并重新计算 |
| 读取游戏快照 | 读取尚未落盘的计算输入；之后每次“试算一次”都会重新读取游戏，再执行独立试算 |

实时来源不会被后台存档推送覆盖；可主动切回存档模式。实时结果对应上方标注的快照时刻，不会在结果中持续增长。

### 2.2 轻量实时读数

进入「工具 → 实时读数」，点“开始读取”。该页默认关闭，约每 200 ms 在上次请求结束后再发起下一次请求。点击停止、离开该页或页面隐藏时停止，保留的数值明确标为上一次读数。

这个页面用于观察金币、魔力、建筑和激活法术；构筑辅助的计算快照另行采集完整得多的计算上下文，二者工作量和耗时不同。

## 4. 核对结果与已修复的问题

### 4.1 核对范围

| 核对方式 | 已有结果 | 如何理解 |
|---|---:|---|
| 原始 pcode 与转写方法返回值差分 | 4,193 个用例精确一致 | 覆盖 3,339 个计算/判定方法及若干参数；主要使用一份 R44/A1 样本 |
| 独立存档解码与转写对象载入比较 | 2,975 / 2,975 字段一致 | 建筑、升级、法术、统计、阵营币及关键全局状态 |
| 当前方法索引 | 3,529 个方法、1,422 个类 | 包括 190 个仍未逐动作核对的状态变更入口 |
| 当前转写清单 | 生成错误 0；解析错误 11 | 11 个资源、翻译或 JSON 相关文件未计入通过 |

pcode 核对是逐方法差分：被测方法直接解释字节码，子调用及 Math 仍使用 Python 对象和运行时，并非完整的 Flash VM 对照。不能据此证明未触发分支或所有时间状态都已正确。

静态初始化还记录了界面显示类 `§7!B§` 的 3 个错误，不在本轮计算核对通过范围内。

### 4.2 本会话修复的关键问题

1. **总产出口径。** 原来约 1700 倍的差距来自只比较建筑收入；游戏底栏总产出还包含助手收入。助手每次收益需使用助手专用点击奖励入口。

   ```text
   总产出/秒 = 建筑产出/秒
              + 助手效率 × 助手每次收益 × 助手数量
   ```

2. **存档读取错位。** 反编译的 `Game.load` 丢失旧雪球大小的 `readUnsignedShort()`，使后续字段错位 2 字节。生成器现在先核对原 pcode 的读取证据，再恢复该操作；没有证据时停止生成。

3. **AS3 语义差异。** 修正 null/undefined、普通与严格相等、空数组/对象真假值、int/uint 回绕、参数及字段类型转换、向量、Date、ByteArray 写入、switch 落空及部分数值运算等行为。

4. **独立初始化遗漏。** 补齐皇家贸易令索引、计算需要的 Main 缓存和桌面平台常量；PlayFab/TimeServer 的计算字段和 getter/setter 不再被普通界面桩吞掉。

5. **真实动作入口。** 修正未混淆方法名映射，避免把 `useSpell` 错映射后被界面桩静默吞掉；购买和施法入口现在检查方法存在。

6. **失败显式报错。** 关键类缺失、模块和索引摘要不一致、过高存档版本、无效目标、过期快照等不再返回默认零值冒充计算结果。

7. **翻译与计算分离。** 计算引擎保持原文命名，最后翻译输出；部分客户端函数按名称找对象，不能直接用汉化替换引擎语言函数。

8. **界面生成。** 修复构筑脚本重复载入及 CSS 被插为脚本的问题；构筑与实时脚本各载入一次。生成记录仍有 29 个专名未找到表格格子，另有一个存档名称显示英文，未在本会话消除。

### 4.3 不应继续沿用的早期结论

| 早期判断 | 当前结论 |
|---|---|
| 总产出低约 1700 倍，可能是皇家贸易令漏乘 | 主要是建筑与助手收入口径未合并 |
| 两套 AS3 的最大魔力分支不同，说明公式版本变化 | 2,488 个同路径文件中 8 个 AS3 文本不同；对应方法体 pcode 未发现指令变化，不能仅凭反编译文本认定公式变更 |
| 小百分比截图差异足以证明一致 | 旧截图与自动存档不同步，法术和时间状态也变化，不是严格基准 |

## 5. 计算性能、缓存和自动征税

### 5.1 性能优化

此前每次试算都会编译并初始化整个客户端模块，重新创建对象、载入存档，并使大量缓存失效。现在复用不可变代码对象、使用源码哈希校验的字节码缓存，并为同一份载入状态保留检查点。

检查点恢复对象、静态字段、容器、引用关系、ByteArray、内存 SharedObject 和随机数位置；查询和动作都在状态事务中进行，异常后也恢复。同一输入的重复查询或动作结果可复用，换输入后清除。

| 操作 | 优化前 | 优化后 | 口径 |
|---|---:|---:|---|
| 首次载入固定存档 | 2219 ms | 1404 ms | 引擎内部，仍需初始化 |
| 首次买 10 栋农场 | 2173 ms | 103 ms | 同一固定存档，约 21 倍提速 |
| 首次征税试算 | 2503 ms | 287 ms | 包含完整试算汇总 |
| 完全相同输入的重复试算 | 需重新初始化 | 约 0.02 ms | 结果缓存命中，不代表状态变化时的计算耗时 |
| 已填好缓存后的数值读取 | 约 81 ms | 约 0.02 ms | 引擎内部，不含界面与进程通信 |

优化前后固定输入结果严格一致；另对当时正在使用的存档比较了缓存与全量路径，基准、农场购买和征税结果一致。

### 5.2 游戏为什么能大量自动征税

客户端在特定自动征税路径中一次计算 `floor(当前魔力 / 本次费用)`，集中扣费、更新次数，再调用一次 `onEffect(次数)`。复制效果也按次数批量追加。该路径有条件限制，且部分奖杯记录仍有小循环，不能概括成所有征税都没有循环。

固定样本的 Python 转写引擎实测：手动一次约 175 ms；自动一次批处理消耗 20,480 魔力，对应 128 次基础费用、含复制共 256 次施法统计，约 174 ms；16 次手动调用约 2763 ms。

这些是本机转写引擎耗时，不是游戏原生耗时。未来连续模拟应调用客户端自动批处理入口，不能把大量手动调用视为等价替代。

### 5.3 已研究但未接入的时间循环

客户端逻辑 tick 为 `1/30` 秒；`onEnterFrame` 累积时间，单次积压限制约 `1/3` 秒，再交给 `advanceTicks`。逐 tick、整秒、法术推进、助手结算、周期缓存失效有各自顺序。部分缓存计数按推进调用次数增加，不能一律按传入 tick 数线性换算。离线 `timeWarp` 也不是精确在线循环的替代。

后续必须按这些规则接入连续模拟，不能用“当前总产出 × 经过时间”代替。

## 6. 存档同步、轻量读数与实时计算快照

### 6.1 存档变化同步

`app/save_sync.py` 使用 Windows 目录变化通知，约 80 ms 合并连续写入；读取前后检查文件身份、长度和修改时间，并校验 Base64/zlib 完整性。缓存、内容版本和递增序号避免重复解码，旧请求不会覆盖新快照。

原生监听有 2 秒检查兜底；旧壳没有推送接口时使用 1 秒读取兜底。真实文件自然保存后，曾在修改时间之后约 149 ms 收到通知；临时文件验证约 124 ms。它消除了额外的 10 秒发现等待，游戏自身约 30 秒的常规保存间隔仍存在。

本机默认存档位于 `%APPDATA%\com.kongregate.mobile.realmgrinder.air\Local Store\#SharedObjects\RealmGrinderDesktop.swf\realm-grinder.sol`。程序也按目录模式发现候选存档。

### 6.2 轻量只读接口

进程访问只申请 `PROCESS_QUERY_INFORMATION | PROCESS_VM_READ`（`0x410`）。验证目标 exe、指针宽度、对象类型、向量数量和 SID；受校验数值同时检查其数值及校验关系。每次新连接重新定位，不使用上次保存的绝对地址。

轻量读取首次定位约 1.5～2 秒，之后每次约 5～8 ms。该接口逐字段采样，不保证所有字段在同一个逻辑 tick。

### 6.3 实时计算快照

快照包含本轮客户端的以下对象及数据：

| 范围 | 本轮数量或内容 |
|---|---|
| 计算类静态数据与缓存 | 599 个类 |
| 建筑 | 25 种 |
| 升级与研究 | 2059 项升级对象，研究在其中 |
| 法术 | 32 项 |
| 奖杯 | 1221 项 |
| 其他输入 | 阵营币、皇家贸易令、三组统计、阵营/飞升/血统、随机数对象、游戏计时等 |

实现要点：

- 按 pcode 声明顺序和 AVM2 存储类型生成槽布局；反编译 AS3 可能重排声明，不能据其显示顺序推算偏移。
- 初次发现所需内存页，随后批量复制到本地内存再解析；页面缓存不落盘。
- 复制前后比较主类字段、资源、tick 计数与 Starling 帧时钟。跨帧、新发现页、受校验数值读取失败会重试，最多 12 次后报错。
- 这是一致性前后校验，不宣称拥有暂停游戏后的原子快照。
- 用 `Starling.mLastFrameTimestamp` 冻结该游戏帧的 `getTimer`，Date 使用采样时刻；避免服务器时间公式继续使用零计时器。
- 保留客户端缓存和失效标志。实时模式不额外强制刷新所有缓存；动作沿用客户端原入口的更新顺序。存档模式保留原刷新路径。
- 在独立对象中核对类型、数量、SID、字段完整性和来源摘要后应用快照；失败不退回旧存档值继续计算。
- 当前未采集活动服务器缓存，因此活动状态非零时明确拒绝实时试算。

实测首次定位、采集和载入约 4.5～5.0 秒；之后重新采集并试算约 1.0～1.7 秒，取决于跨帧重试次数。最新记录为 4.95 秒、1.66 秒，输入解析约 193 ms，批量复制约 5.2 ms。

### 6.4 人工配合与程序内验收
