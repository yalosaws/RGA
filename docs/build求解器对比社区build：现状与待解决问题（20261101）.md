# build 求解器对比社区 build：现状与待解决问题（2026-11-01）

> 最新要求已撤回社区保底和当前配方种子：求解器改为完全冷启动，社区仅供搜索结束后的外部对照。见 [独立冷启动与购买时序验收](build求解器独立冷启动与购买时序验收（20261101）.md)。下述保底模式仅为历史记录。

> 后续接手进展（2026-11-01）：严格模板入口、147 个购买组合自检、多时长独立比较及活动排期修正已经完成，见 [社区build严格评测与对照](社区build严格评测与对照（20261101）.md)。随机择优按用户本轮选择继续暂缓。下文保留原交接记录，原“3600 秒不合常理”的推断已被后续实验修正：瞬时产出允许下降，且旧模拟另有缺排期导致活动被提前清除的问题。不能沿用原表直接宣称超越社区。

> 后续重构：多时长独立种群、间接公式关系、显式社区保底与同预算对照见 [多时长重构与验收](build求解器多时长重构与验收（20261101）.md)。

写给接手的人。背景：RGA「按目标找 build」的求解器（`scripts/rg_search.py`，说明见 [build求解器重构与验收](build求解器重构与验收（20261101）.md)）能不能超过社区模板（`docs/A1-build-templates.json`，来自 `docs/A1Templates.txt`）。本文记录这次实测怎么做的、得到什么、**哪些结论不可信**，以及要接手解决的问题。没有改任何源码，实测脚本在会话临时目录里，复现方法见末尾。

## 1. 一句话结论

在固定随机流、目标为「总产出」、搜索时长 300 秒的条件下，求解器搜出的 build 在 300～1800 秒内产出高于社区 R60-62 DNTT（e57+），最多约 13 倍；60 秒和 3600 秒没有超过。**但这个比较有两处没解决的缺陷（第 3、4 节），不能当成「已经超越社区」的结论。**

## 2. 实测条件与数据

- 存档：`build/mechanics-audit/input.sol`（A1 R60，SHA256 `97314afa…cb1`）。引擎：原生（C++）游戏模拟，`rg_goal.Runner.run`，执行策略沿用求解器（每 2 秒「全部购买」，恢复存档的自动施法设置，不模拟手动点击、挑战操作）。
- 目标：`production`（总产出，每秒）。
- 社区 build：`R60-62 DNTT (prod, e57+)`，32 项研究。名字里 `DN` = 矮人血统，`TT` = 泰坦阵营（前血统后阵营，两个字母各自的代号见 `a1_templates.py` 和攻略要点）。模板里没有立场、显赫，实测按 `alignment=neutral, faction=Titan, bloodline=Dwarven, prestige=Dragon, merc=[]` 跑。
- 求解器：`benchmark_build_search.py --algorithm population --goal production --at 300 --budget 240`，用时 225 秒、845 局。搜到的方案：中立、无面者（Faceless）、龙族显赫、德鲁伊血统，31 项研究。

| 时长 | 社区 | 求解器（只针对 300 秒搜） | 存档原 build |
|---|---:|---:|---:|
| 60 秒 | 2.1e153 | 1.4e152 | 3.9e135 |
| 300 秒 | 3.1e154 | **3.3e155** | 2.2e135 |
| 900 秒 | 6.1e154 | **7.8e155** | 2.2e141 |
| 1800 秒 | 1.5e155 | **9.4e155** | 5.8e141 |
| 3600 秒 | **3.5e154** | 2.3e151 | 1.1e137 |

要点：
- 求解器只对 300 秒搜过，60 秒输、3600 秒输都在预期内；要比哪个时长就要对哪个时长各搜一次。
- 3600 秒时三套 build 的值都比 1800 秒**更低**，不合常理（产出应该随时间单调增长）。可能是长时模拟或「总产出」指标的问题，**未核实，这一行不要引用**。

## 3. 问题一：研究买不全，而且是静默的（用户最担心）

**现象。** 第一次跑社区 build 时我没设龙族显赫，结果 `ok=True`、`value=3.19e128`，但 `skipped = ['S1450','C1300','C1500','D1175','E1225']`——5 项研究没买到，数值比正确结果低 26 个数量级。没有任何报错，只是返回字典里多了个 `skipped`。加上 `prestige='Dragon'` 后 32 项全买到，`value=3.10e154`。

**原因。** 编号 1000 以上的研究（`S1450`、`C1300`…）是龙族研究，要先选龙族显赫才能买（`rg_goal.py` 里 `LATE_PRESTIGE`、`late_prestige` 逻辑，约 226–230、364–389 行：龙族显赫要等研究买完、或有「地下世界的秘密」才选）。模板本身不写显赫，是调用方根据研究内容推断的。

**为什么危险。**
1. `Runner.run` 对「买不到」只在 `out['skipped']`（研究）、`out['skipped_merc']`（佣兵）里记一笔，仍然 `ok=True`、照常给数值。调用方不看 `skipped` 就会拿到被少买了研究的结果，并且看上去完全正常。
2. 研究能不能买取决于很多运行时条件：研究所是否显示（`research_ready`，约 359–362 行）、是否选了对应阵营/显赫、有没有「地下世界的秘密」、佣兵局要对应的 Secrets 升级、`RESEARCH_WAIT` 秒内等不到就整批放弃（约 378–380 行，同一批全丢）。任何一条没满足都会静默丢掉研究。
3. 求解器内部（`rg_search.py` 约 122–137 行）对 `skipped` 的处理是：把没买上的研究从方案里删掉后重新整局跑，不让榜单带着买不到的项。这对**求解器自己的候选**是对的，但**外部输入的模板**（比如这次的社区 build）没有同样的保护——我这次就是手动发现 `skipped` 才察觉的。

**待做。**
- 评测任何「别人给的 build」时，必须强制检查 `skipped == []` 且 `skipped_merc == []` 且 `ok`，否则视为配置错误、直接报错，而不是出数。建议封装成一个「评测给定模板」的入口（现在只有搜索入口）。
- 做一个自检：对 `A1-build-templates.json` 里每份研究模板和佣兵模板，枚举合理的（立场、阵营、血统、显赫）组合，列出每份模板在这份存档上「全部买到」的组合；买不到的写明原因（缺哪个解锁）。这样才知道哪些社区 build 在当前存档上本来就不能用，不会再犯这次的错。
- 研究所的购买顺序、龙族显赫要等研究买完才选这条规则，是否会让「模板里既有龙族研究又没有 Secrets」的组合死锁，需要确认（这份存档有 Secrets，所以没触发）。

## 4. 问题二：随机法术和固定随机流

**现象。** 所有试跑共用同一条随机流（`Runner(seed=…)`，原生引擎用 MT19937，和 Python `random` 逐位相同）。求解器搜出的方案可能只是对这条流碰巧好；社区 build 里依赖随机效果的部分也只被抽了一次样。用户指出：法术可以重置，所以实际玩时完全可以重摇到最好结果。**要求：随机法术一律按最好效果算。**

**引擎里的随机点**（从 `build/installed-as3-named/scripts` 查到，随机数都走游戏自己的 `Rand` 类，每个法术/升级各有一个实例）：

| 位置 | 随机什么 |
|---|---|
| `LightningStrike.getEffect` | 从有建筑的层级里随机挑被劈的建筑 |
| `Maelstrom` | 随机挑若干建筑，再随机定类型（0～3） |
| `DivineMiracle` | 随机挑一种建筑层级 |
| `DragonsBreath.onEffect` | 随机挑龙息颜色（每组 6 色里没用过的） |
| `Catalyst`、`ChaosMadness`、`LimitedWish` | 各自随机挑效果 |
| `FacelessFaction04` | 随机数 |
| `GoblinUpgrade9`（地精升级 9） | 每 120 tick（挑战 1 时 30 tick）随机给 1～1500 倍金币；离线时 2000～10000 |
| `Game.as` 的精灵幸运、阵营币、考古等 | 和点击/考古相关的概率，当前模拟不手动点击 |

用户选定的口径：「逐个试、选产出最高」——每个随机点把所有候选各试一遍，留下当时总产出最高的。

**为什么没做。** 要改原生（C++）引擎：`scripts/as2cpp.py` 从游戏 AS3 转写 C++，随机调用在 `scripts/native/rt.cpp` 的 `RNG` 和生成代码里；「逐个试」需要在随机点做快照（`StateSnapshot`）、逐候选施放、比较、回滚，再选最好的。改完要重新验证原生与 Python 版逐 tick 一致，并重新校准求解器的验收数据（现有的精确回放比对依赖固定随机流，口径会变）。用户已决定先不做，没有开工。

**待做（接手前先和用户确认「最好」的口径）：**
- 先列清楚每个随机点的候选集合和判优标准（总产出？还是随目标变，如魔上限、回魔？），再决定放 Python 层还是 C++ 层。
- 先只做影响最大的几个（雷击、龙息、地精升级 9），看数值有没有大变化，再决定要不要全做。
- 在此之前，**所有对比结果只能标注「固定随机流」**，不要宣称超越社区。
- 临时替代（比不改引擎弱）：多种子重跑，对社区 build 和求解器 build 各取最好/中位。我写过脚本（第 7 节）但没跑完，被用户中断。

## 5. 其他限制（沿用之前验收文档，这里不重复展开）

- 结构枚举只覆盖 9 个基础阵营及其匹配显赫、3 种佣兵立场、12 种血统加不选血统（273 种），没有 A2/A3 端到端验收。
- 目标检查分辨率：魔力/助手每秒，产出/宝石每 5 秒；总产出是慢目标，一局约 0.5～0.6 秒。
- 社区模板的目的不一定是纯产出：还兼顾宝石、法术配色（龙息要配色、雷击瞄龙巢）、世系练级、佣兵解锁、挑战。「同一产出指标」上的胜出不等于「更好的 build」。
- 只测了一份存档、一个目标（总产出）、没有手动点击、挑战、主动择色。

## 6. 建议的接手顺序

1. 封装「评测给定模板」入口，强制检查 `ok`、`skipped`、`skipped_merc` 为空；跑第 3 节的模板自检，输出每份社区模板在当前存档上的可用组合。
2. 用修正后的入口重做社区 build 对比，覆盖多个模板（不只是 DNTT）、多个目标时长（60/300/900/1800）、每个时长各搜一次。
3. 查 3600 秒数值下降的原因，在这之前不要报 3600 秒的数据。
4. 经用户确认口径后，实现随机点「取最好」，重新校准验收。

## 7. 复现

存档和引擎文件在仓库里；下面是我用的两个脚本核心（放在任意目录运行，路径按需改）。

评测社区模板（关键是 `prestige='Dragon'` 和检查 `skipped`）：

```python
import sys, json
sys.path.insert(0, 'scripts')
from pathlib import Path
ROOT = Path('.')
import rg_sim
rg_sim.MEMBER_NAMES = ROOT / 'build/calculation/member-names.json'
import rg_goal
tp = json.load(open('docs/A1-build-templates.json', encoding='utf8'))['research']['R60-62 DNTT (prod, e57+)']['tp'].split(',')
r = rg_goal.Runner(ROOT/'build/calculation/game.py', save_path=ROOT/'build/mechanics-audit/input.sol',
                   research_json=ROOT/'build/calculation/research.json')
plan = dict(alignment='neutral', faction='Titan', bloodline='Dwarven', prestige='Dragon', research=tp, merc=[])
o = r.run(plan, 'production', float('inf'), 300)
assert o['ok'] and not o['skipped'], (o['note'], o['skipped'])   # 这行就是第 3 节要强制的检查
print(o['value'])
```

求解器搜索：

```powershell
python -X utf8 scripts/benchmark_build_search.py --algorithm population --goal production --at 300 --budget 240 --output <输出.json>
```

输出里 `best[0]['plan']` 就是搜到的方案，可直接作为上面 `plan` 在其他时长下评测。多种子对比把 `rg_goal.Runner(..., seed=k)` 换种子重建即可（每个种子要新建 Runner）。
