共同条件：

- 同一份 A1 R60 固定存档，SHA256：`97314afa8d80b5192db18fb862119c963386771ccd27361159936023322b7cb1`。
- 存档时间固定，全部游戏随机流由同一基准快照恢复。
- 同一份原生引擎二进制、同一份游戏公式和依赖图；没有启用粗跑。
- 6 个低优先级计算进程。
- 都枚举相同的 273 种结构。
- 调优总配置都是 60 秒、深入逐项检查预算都是 0。
- 新版本从原 60 秒预算中给分支交叉预留 20 秒；原来的单项调优用其余 40 秒。各阶段按完整批次执行，是软预算。

改动前代码和二进制冻结在 `build/benchmarks/build-search/variants/before`；改动后在 `variants/after-budgeted`。每份目录有文件哈希清单。不要把当前正在改的源码当成旧版本来重新测试。

## 实际改动

`scripts/rg_optimize.py` 新增 `recombination_candidates`、`Optimize._recombine`，并在调优后、深入检查前接入：

1. 取当前前 3 名，把同阵营其他血统/显赫组合已经验证过的研究方案作为候选来源。
2. 尝试整套研究替换，或一个研究分支整体替换；一次可以同时调整多项。
3. 研究预算、购买门槛、购买顺序、资源不足，都交给原来的实际购买和整局模拟处理。
4. 只接受精确整局结果更好的方案；保留原来已找到的最好结果。
5. 最多 4 轮，在原调优预算内安排；已有试跑缓存继续复用。

这一步补充的是单项增删换不容易跨过的组合。没有把单项估值、近似增长模型或新的评分公式当成最终数值。

先做过一个“无条件追加阶段”的版本：魔上限从 23555552 提高到 24081643，但完整搜索变成 143.13 秒，因此没有保留这种时间安排。最终版本使用上表的预算分配。

也试过同时交换两个分支，在回魔当前最好的方案上额外验证 162 套，没有继续提高最好值，因此没有把这部分额外开销接入程序。

- 比较要求精确相等，不使用相对误差容忍。
- 全部一致，固定存档哈希和时间未改变。

证据：`build/benchmarks/build-search/replay-verification.json`、`replay-verification-final-mana.json`。结构化汇总：`comparison.json`。
