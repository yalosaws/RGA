# 新的配 build 方法：从「量的网络」出发（2026-11-01，设计稿；第一版实验结论见文末）

## 起因

现在的「按目标找 build」靠估算给初始方案，再靠整局跑一项一项试（标准深度约 2.9 万次）。问题是它看不懂加成之间的关系，只能碰运气：
- 2026-11-01 修了依赖图的一个漏洞（`Utilities.getMaxMana` 等写法没认出来）后，回魔「快速」搜索的最好结果从 14.3 亿变成 512 亿（德鲁伊 + 德鲁伊血统 + 龙族显赫）。旧版不是没跑这个组合，而是给它配的研究里没有加魔上限的，整局成绩一般，就没进调优。**一个组合好不好，取决于有没有配上和它「咬合」的东西**，逐项试很难同时想到。
- 研究之间严格的支配关系一对都没有（见 `docs/按目标找build（20261030）.md`），靠剪枝省不了多少。

所以换个思路：先把游戏里所有加成读成一张「量的网络」，从网络结构里推出哪些东西会互相放大，再按这个去配。

数据来源：`scripts/rg_catalog.py` 从客户端导出的全部阵营升级、血统、传承、条约 / 联盟、世系和天赋、独特建筑（`build/加成目录.md`，344 项），加上 `docs/研究公式（客户端）.json` 的 264 项研究。

## 读下来的规律

### 1. 所有加成都是「某个量 → 另一个量」

几乎每一项的效果都是：读一个量 x，按一个公式 f(x) 给另一个量 y 加（`y += f(x)`）或者乘（`y *= 1 + 0.01·f(x)`）。公式只有几种形状：
- 常数（如 AN5 回魔 ×1.5）；
- 幂次 a·x^p，p 多在 0.25～0.9 之间，个别大于 1（奥林匹斯圣殿 6·皇家贸易令次数^1.2、德鲁伊特权1 1.5·时间^1.5、龙族 DG5 遗物数^1.25）；
- 对数 a·ln(1+x)^k，k 在 1～6 之间。

被读的量（x）可以分成三类：
| 类 | 例子 | 一局里怎么变 |
|---|---|---|
| 存档里定死 | 宝石、奖杯、遗物、考古深度、重生次数、已花研究点数、世系等级、本R各立场时间 | 不变，只决定「水平」 |
| 随时间积累 | 本局时间、产生的魔力、fc 总数、点击次数、施法次数、皇家贸易令次数、建筑数 | 越来越大 |
| 当场算的中间量 | 魔上限、每秒回魔、助手数、fc 获得率、产出、皇家贸易令加成、法术持续时间、生效中的法术数 | 由上面两类和加成算出来 |

被加的量（y）只有十来个：魔上限、回魔、助手数、助手产量、fc 获得率、总产出、各建筑产出、点击产出、法术持续时间 / 消耗、皇家贸易令加成、价格。

### 2. 中间量之间连成了环

把「读 x、加 y」画成箭头，几个中间量互相指向，形成正反馈环。例子（括号里是代表性的项）：

- **魔力环**：魔上限 →（德鲁伊血统：回魔 ×(0.25·M^0.5 + 0.0025·ln(M)^5)%；D300）→ 回魔 → 产生的魔力（积累）→（无面者血统：魔上限 + 0.5·ln(产生的魔力)^4）→ 魔上限。
- **助手环**：魔上限 →（A120：助手 + M^0.5）→ 助手 →（FC7、DD6：回魔 + 3·助手^0.4；W205；S5625 回魔 ×助手^0.25）→ 回魔 → 产生的魔力 →（A375、C1325、S13125：助手 + ln(产生的魔力)^k）→ 助手。
- **产出环**：产出 → 金币 → 建筑数、皇家贸易令次数 →（泰坦血统 产出 ×12·次数^0.8；奥林匹斯圣殿；卓尔蛛后爱巢）→ 产出。
- **回魔 → 产出**：大量项按回魔或魔上限加产出（AN6、DD5、DW3、DN11、DG12、矮人熔炉 300·回魔^0.6、残骸工坊、巨石阵 30·M^0.6、S135、S700、S150、S180）。

环的强弱看箭头上的「弹性」：y 对 x 的对数导数 d ln y / d ln x。幂次 x^p 的弹性约等于 p 乘这一项在 y 里的占比；对数 ln(x)^k 的弹性是 k / ln x，x 越大越弱。一个环里弹性相乘接近或超过 1 时，几个量会一起越滚越大。

### 3. 有些加成只改「别人看到的值」

`Utilities.getAssistantsNum` 在 `Formulas.getAssistantsNum` 之上再乘泰坦 TT7（×3）、精灵 EL11（×11）、仙灵特权5（×4）、亡灵高级遗产；`Utilities.getMaxMana` 再乘卓尔特权5（×4）。它们不改助手数、魔上限本身，只改其他加成读到的值。单独看它们对目标「没用」，配上读这个量的加成才有用，是典型的「要两项一起才显出来」。

### 4. 门槛

不少项有条件：E450 要魔上限 4 万，龙族显赫要另外三族的第三个条约，世系要同阵营皇家贸易令 400 次，组合研究要前置研究解锁过。门槛也是网络里的量，能预测它什么时候到。

### 5. 积累量的增长速度差别很大

- 时间：线性。
- 产生的魔力：回魔对时间的积分。回魔越涨越快，它就涨得更快。
- 建筑数、皇家贸易令次数：价格按几何级数涨，数量只随金币的**对数**增长，涨得很慢。所以按建筑数加成的项在一局里变化不大，接近常数。
- fc 总数：按 fc 获得率和点击 / 施法积累。

## 新方法：用「量的网络」的近似模型配 build，再整局验证

### 第 1 步：建网络（一次性，游戏更新后重跑）

扩展 `rg_catalog.py` / `rg_depgraph.py`：对每一项，记下「读哪些量、加到哪个量、加还是乘、公式」。公式用已有的解析器（`research_formulas.Parser` + `rg_dominance` 的展开和变量分类）转成表达式树，变量对到网络里的量（魔上限、回魔、助手、产生的魔力……）。

### 第 2 步：在参考轨迹上线性化（每次搜索，几秒）

拿一局整局跑（现在每个阵营单位本来就要跑）的几个时刻的状态，算：
- 每一项对每个量的直接贡献 a（在状态上切换拥有标记、重算，和现在的估算一样，准确）；
- 每一项的效果对它读的量的弹性 b（从公式求导，不用跑）。

于是一套方案 S 下，各中间量的对数变化近似为
  Δln Q = A·x + B(x)·Δln Q  →  Δln Q = (I − B(x))⁻¹ · A·x
x 是「选了哪些项」的 0/1 向量，A 是直接贡献，B(x) 是选中项连起来的弹性矩阵。(I − B)⁻¹ 就是环的放大作用：单独看都不大、但连成环的几项，放在一起会被它放大。积累量（产生的魔力、fc 总数）按参考轨迹上的时间分布折算。

### 第 3 步：在模型上整体寻优（几秒）

目标值的对数 = 模型给出的 Δln(目标)。在这个模型上一起选结构（立场、阵营、血统、显赫、世系）和研究、佣兵：
- 模型很便宜（矩阵运算），可以对 273 种结构各做完整的研究 / 佣兵寻优（分支定界或整数规划），不再一项一项试；
- 门槛作为约束：模型预测某个量在规定时间前到不了门槛，就不放依赖它的项；
- 会主动找「读者 + 供者」的配对：比如选了德鲁伊血统（读魔上限），模型里魔上限的每一点提升都会经它放大成回魔，加魔上限的研究自然排上来。这正是旧方法漏掉的那种情况。

### 第 4 步：整局验证，修正模型

模型给出每种结构的前几套，整局跑验证；实测和模型预测的差用来修正 A、B（以实测为准），再在模型上重新寻优，几轮收敛。最后的数值一律以整局跑为准，和现在一样。

### 额外的好处：能解释

模型知道每一项为什么有用：「德鲁伊血统 ×42，因为魔上限 1.07e7；D270、W1400 经魔上限再放大 ×1.4」。界面上可以把这条链显示出来，比现在的「贡献 ×1.39（驱动 / 填空格）」好懂。

## 验证计划

1. 只做第 1、2 步，在用户存档上对 273 种结构算模型预测，和已有的整局跑结果比排名（期望：前 10 名基本对上）。
2. 检查模型能不能自己找回「德鲁伊 + 德鲁伊血统 + 魔上限研究」，以及魔上限目标下的「无面者 + 亡灵血统 + 龙族显赫」。
3. 接入搜索：模型寻优 + 少量整局验证，对比现在的方法，看最终数值和整局跑次数。

## 风险

- 线性化只在参考状态附近准；差得远的方案（比如换了阵营）要用它自己的参考轨迹，现在每个阵营单位本来就各跑一局，可以复用。
- 法术（自动施法、雷击换目标、生效中的法术数）是开关式的，不好线性化，先当成按时间平均。
- 公式解析覆盖不了的项（多行代码，约 1 成），先用切换标记得到的直接贡献，弹性记为 0。

## 实验结论（2026-11-01，用户存档 A1 R60 固定副本，第 60 秒，273 个结构逐个整局跑）

实验脚本（未进 scripts）：对每个阵营单位跑一局参考轨迹，在末状态上对每个结构分别用三种办法求方案，再各整局跑一次。

1. **瞬时的那一半网络，游戏公式本来就算准了。** 估算是在一个真实状态上切换拥有标记、用游戏自己的公式重算，魔上限、回魔、助手之间的互相引用当场就闭合了，(I − B)⁻¹ 那一步不用另做。之前漏掉「德鲁伊血统 + 魔上限研究」，原因是依赖图没把 `Utilities.getMaxMana` 等写法认成中间量，加魔上限的研究没进候选（已修）。修复后估算排名和整局结果的 Spearman 相关：回魔 0.63 → 0.98，魔上限 0.95。
2. **积累量按速率缩放（产生的魔力、fc 总数、金币，迭代到稳定）不改变任何选择**：273 个结构给出的方案和现在的估算逐项相同，只是数值整体变了。第一版的「网络模型」不值得接入。
3. **真正有效的是估算时把空格填上**（`solve_static(fill=True)`，现在估算阶段用的是 `fill=False`，空格留给调优阶段一项一项加）：
   - 魔上限：191 个结构整局成绩变好、0 个变差，平均 ×1.75；最好的「德鲁伊 + 无面者血统 + 龙族显赫」不经调优就到 1.97e7（原流程调优 60 秒后 2.07e7）。不填空格时有 28 个结构整局跑失败（研究太少凑不出龙族条件）。
   - 回魔：195 个变好、9 个变差，平均 ×1.10；但最好的「德鲁伊 + 德鲁伊血统 + 龙族显赫」从 2.49e10 掉到 1.11e10，填的空格里有实际有害的项。
   - 所以填空格应当两套都整局跑、取好的（每个结构多跑一次，6 个进程约多 15 秒）。

## 实验二：直接跳到终态（2026-11-01，脚本在会话临时目录 `jump.py`，未进 scripts）

开局逐秒跑到选完、买完（第 8～38 秒）；之后只在按 2 倍间隔取的时间点之间跳（例如 10→20→40→80→160→300 秒）。每个点真跑一秒，量出各累计量每秒涨多少（统计数组、阵营币、各法术施放次数和时间），这一段按两端速率平均乘时间；金币做不动点：按估出的累计金币「全部购买」买满，按新产出重估，3 轮。生效的法术当成一直在放。

回魔，20 个不同结构：
- **第 300 秒：比精确整局跑快约 17 倍**（每套 0.03～0.09 秒）。法术稳定的方案误差 0.3%～6%，排名相关：对终点值 0.958，对后半局平均 0.977。
- **第 60 秒：只快 3.8 倍**，开局逐秒那段占了大头；按后半局平均，误差平均 3.5%，排名相关 0.979。
- 失准的一类是回魔来回跳 3 倍的方案。原因是**龙息每次重放随机选颜色，「蓝」是回魔按倍数加成**，生效的法术一直是同一组，变的是龙息当前的颜色。跳跃估算把颜色定格在第一次抽到的那种。精确跑的「第 T 秒回魔」本身也带这份运气。

要再快：开局也不逐秒跑，直接把选择套上（估算本来就这样切换拥有标记），60 秒目标才有可能到几十倍。龙息这类随机效果应当按各颜色的期望算，目标值也应改成不受运气影响的口径。

### 实验二续：开局也直接跳（2026-11-01）

存档恢复、退位后，不逐秒推进，直接把立场、阵营、血统、显赫、研究、自动施法买上：走游戏的 `buyUpgrade`（跳过「看得见」检查），金币、阵营币暂时给足，买完还原，这样 `onPurchase` 的附带效果都照常发生，例如挑战奖励、龙族传承。只切换拥有标记的话，这些会缺，德鲁伊的方案会低 90%。佣兵升级要先有建筑才买得上，所以每个时间点重试。然后从第 0 秒按 2 倍间隔跳。每个时间点只量「推进一秒」本身的增量，购买是一次性的，不能当速率外推；金币的不动点迭代到变化不足 1%，累计金币只增不减，金币不低于 0（负金币会让游戏把产出判成 0）。

20 个不同结构：

| 目标 | 提速 | 结果 |
|---|---|---|
| 回魔第 60 秒 | 3.7 倍 | 对终点值平均误差 4%，排名相关 0.974 |
| 回魔第 300 秒 | 14 倍 | 排名相关 0.94～0.97，误差主要来自龙息颜色 |
| 魔上限第 60 秒 | 2.8 倍 | 前 6 名误差都在 2% 内，其余 11 套偏低 25%～91% |
| 魔上限第 300 秒 | 12.7 倍 | 排名相关 0.94 |

- **间隔不能大**：开局几秒有「金币 → 建筑 → 产出 → 收税金币」的强正反馈，精确跑第 8～16 秒金币涨 1e27 倍。用 4 倍间隔时，不动点收敛到偏低的值；用 2 倍间隔，无面者那套第 60 秒魔上限和精确跑一样（6.07e6）。
- **偏低的那一类**：阵营币和皇家贸易令互相放大（精确跑 9、10 号阵营币第 20～60 秒涨约 5 万倍，跳跃估算只涨 3 倍），凑不够龙族联盟要的 5e15，后面一串龙族加成都没拿到。只对金币做不动点不够；对阵营币也做的话，每一轮都要真跑一秒（约 2.4 毫秒）才能量出速率，速度优势就没了。
- **每看一次状态至少 1～2 毫秒**：收税每次施放都清缓存、重算总产出，重算一次总产出要调用约 9500 次 `hasUpgrade`。跳跃省掉的是「看的次数」，单次的成本省不掉。60 秒的目标总共只有 60 次，跳跃最多省到十几次，所以只快 3～6 倍；300 秒的目标能快 13～20 倍。

结论：直接跳在增长平缓的方案上又快又准，但遇到强正反馈（金币 ↔ 建筑、阵营币 ↔ 贸易令）必须小步走，60 秒的目标快不了几十倍。要到几十倍，得同时降低每次全量重算的成本（引擎里 `hasUpgrade` 之类的热点），或者只对候选里少数几套用整局跑。

## 定位和后续研究（2026-11-01 用户确定）

「按目标找 build」的主线是种群搜索 `scripts/rg_search.py`（见 `docs/build求解器重构与验收（20261101）.md`），评分全部用精确整局。本文的实验（积累量模型、跳跃估算、只用估算）和粗跑（`rg_goal.Runner.run(coarse=D)`、实验开关 `RGA_COARSE`，主线显式传 `coarse=0`）作为后续研究资料保留。

已核对：用验收报告的同一存档（`build/mechanics-audit/input.sol`）按后半局平均比较，新版最好方案比旧版好 36%～40%（终点值只好 15%～19%），提高是真的，不是龙息颜色的运气。

后续研究方向（按价值排序）：
1. **目标口径**：回魔等目标按「第 T 秒那一刻」打分，龙息每次重放随机选颜色（蓝色按倍数加回魔），同一方案相邻几十秒能差 3 倍；新旧两版的最好方案终点都正好落在峰值上。改成后半局平均或按颜色期望，排名更稳。
2. **长时间目标**：300 秒回魔标准预算下比旧版低 7%。可以试粗跑预筛（每 10 秒一步，排名相关 0.99，快约 4 倍），只用来排提案顺序；入榜和最终评分仍用精确整局，避免种群从带误差的数值里学偏（旧搜索里全换粗跑，300 秒回魔低 19%）。
3. **结构范围**：仍是 273 种结构，后续阵营、额外血统 / 契印 / 佣兵法术未纳入；A2/A3 没有端到端验收。
4. **引擎**：83% 在不走缓存的总产出重算；精确复用最多快约 1.25 倍，编译层面（PGO、跨文件内联）约 1.2～1.5 倍，见 `docs/C++引擎设计（20261031）.md`「重算热点分析」。
